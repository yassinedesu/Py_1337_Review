When do top-level imports execute?

Incomplete

Why absolute vs relative — the real difference

Your first answer focused on what re-exporting achieves (convenience), not on the difference between the two import styles. The actual distinction: relative imports (., ..) are portable — if you rename the package, they still work. Absolute imports hardcode the package name and break on rename. PEP 8 recommends absolute imports for top-level code, relative for intra-package references.

sys.path — where Python searches for modules

When you run python3 ft_alembic_0.py from the root, Python automatically adds that folder to a list called sys.path. That is the reason import elements finds the root elements.py. The subject explicitly forbids modifying sys.path — know why: it would let you fake import paths, which breaks reproducibility.

import sys
print(sys.path)
# ['/your/project/root', '/usr/lib/python3.x', ...]
Review

sys.modules — the module cache

Every module Python loads gets cached in sys.modules. This is why the late import trick works: by the time validate_ingredients() is called, light_spellbook is already fully loaded and sitting in sys.modules. Python just reuses it — no re-loading, no crash.

import sys
print(sys.modules.get('alchemy.elements'))
# <module 'alchemy.elements' from '.../alchemy/elements.py'>
Review

Other ways to fix circular dependencies

You used the late import approach. The evaluator may ask you to name the others:

1. Restructure — extract shared logic into a third module that neither file imports from the other.

2. Late import — move the import inside the function (what you did in light_validator.py).

3. Import the module, not the name — import module instead of from module import name; access the name at call time via module.name().

Review

The __all__ variable

You didn't use it in your project, but evaluators may ask about it. __all__ is a list you can define in __init__.py to explicitly declare what gets exported when someone does from alchemy import *. Without it, everything that doesn't start with _ is exported. It's the explicit alternative to selective re-exports.

# alchemy/__init__.py
__all__ = ["create_air", "heal", "strength_potion", "lead_to_gold"]
📖 Concepts & their official names
Term What it means
Package A folder containing an __init__.py — tells Python it's importable as a module.
Module Any single .py file that can be imported.
Absolute import Full path from project root: from alchemy.elements import create_air.
Relative import Path relative to current file using dots: from .elements import create_air.
Re-export Importing in __init__.py so users can access it directly from the package.
Circular import Module A imports B, and B imports A — crash at load time.
Late import Import placed inside a function body — runs at call time, not load time. Fixes circular imports.
sys.path List of folders Python searches when resolving import X.
sys.modules Cache of all already-loaded modules. Prevents re-loading and enables the late import fix.
__all__ Optional list in a module declaring what from module import * exports.
Static analysis Checking code without running it — what mypy and flake8 do.
noqa: F401 Flake8 inline comment to suppress "imported but unused" on re-export lines.
AttributeError Runtime crash when accessing a name that doesn't exist on a module or object.
ImportError Runtime crash when Python cannot complete an import — e.g. circular dependency.
Type annotation Hints like def f(x: str) -> list[str] — checked by mypy, ignored at runtime.
