01Packages & __init__.py

Module vs package

  • A module is a single .py file you can import (elements.py).
  • A package is a folder containing an __init__.py. It groups modules together (alchemy/).

The __init__.py file runs once, the first time anything in the package is imported. Whatever names it defines become attributes of the package: after import alchemy, you can write alchemy.something only if something exists inside that file.

Re-exporting: the public interface

alchemy/__init__.pylines 5–8
from alchemy.elements import create_air  # noqa: F401
from alchemy.potions import healing_potion as heal  # noqa: F401
from alchemy.potions import strength_potion  # noqa: F401
from alchemy.transmutation import lead_to_gold  # noqa: F401

These lines pull names up to the package's top level, so users don't need to know your internal layout.

Without re-exportWith re-export
from alchemy.transmutation import lead_to_goldfrom alchemy import lead_to_gold
from alchemy.potions import healing_potionalchemy.heal()

This is exactly what you worked out yourself with lead_to_gold: the sub-package's __init__.py does from .recipes import lead_to_gold (line 4 of alchemy/transmutation/__init__.py), so you can skip the recipes step.

Aliasing with as

healing_potion as heal doesn't copy anything. It adds a second name, heal, pointing at the same function. That is the "package alias" required by ft_distillation_1.py.

Hiding things on purpose

create_earth lives in alchemy/elements.py but is not imported in alchemy/__init__.py, so it isn't an attribute of alchemy:

ft_alembic_4.pyline 21
print(f"Testing the hidden create_earth: {alchemy.create_earth()}")

Result: AttributeError: module 'alchemy' has no attribute 'create_earth'. The function exists; it just isn't part of the public interface.

Why # noqa: F401

flake8 rule F401 means "imported but unused". In __init__.py the imports are never used in the file itself; their whole purpose is to be re-exported. noqa: F401 tells flake8 "I know, this is intentional."

Concept you didn't use: __all__

An alternative way to declare the public interface is a list in __init__.py:

__all__ = ["create_air", "heal", "strength_potion", "lead_to_gold"]

It controls what from alchemy import * exports, and it also tells flake8 the imports are deliberate, so the noqa comments would no longer be needed. Worth knowing the name in case the evaluator asks for an alternative.

02Import pathways

The three import shapes

SyntaxWhat you getHow you call it
import elementsThe whole moduleelements.create_fire()
from elements import create_waterJust that namecreate_water()
import alchemy.elementsModule inside a package, full path keptalchemy.elements.create_earth()

That's the difference between ft_alembic_0 / _1 / _2 / _3. Same idea, different syntax.

Where does Python look? sys.path

When you run python3 ft_alembic_0.py, Python builds a list of folders called sys.path. The first entry is the folder containing the script you ran, so here, your project root. For every bare import X, Python walks that list in order and takes the first match.

That's the answer to "why does import elements give the root file?"

The root folder is on sys.path, so elements.py there is found. The file alchemy/elements.py is not on the path as a top-level name. Its real name is alchemy.elements.

alchemy/potions.pylines 3–4
import elements                                    # root elements.py  (fire, water)
from .elements import create_earth, create_air   # alchemy/elements.py

Two files with the same name, two different addresses: no dot means "search from sys.path", a dot means "start from my own package."

Be honest about this in the evaluation

import elements inside alchemy/potions.py only works because you launch scripts from the project root. It's a deliberate teaching trick from the subject (the subject forbids touching sys.path, so this is the allowed way to reach the root file). In real projects you'd avoid depending on the launch directory.

Importing a submodule runs its parents first

from alchemy.potions import strength_potion makes Python load, in order: alchemy/__init__.py, then alchemy/potions.py. Parent __init__.py files always run first. This detail matters for the circular import in the next section.

Nested imports (Part II)

ft_distillation_0.py imports potions.py, which imports elements files, which return strings. Python follows the chain automatically: each file runs its own imports when it is loaded.

Imports are cached: sys.modules

The first time a module loads, Python stores it in a dictionary called sys.modules. Any later import of the same module reuses that object instead of running the file again. This cache is the hidden hero behind circular imports (section 04).

03Absolute vs relative imports

Two ways to write the same address.

Absolute

Full path from the top of the project.

from alchemy.elements import create_air

Relative

Path from the current file, using dots.

from .elements import create_air

The dots

DotsMeaningFrom inside alchemy/transmutation/recipes.py
.my own packagealchemy/transmutation/
..my parent packagealchemy/
...grandparentthe project root (not importable here)
alchemy/transmutation/recipes.pylines 3–5
import elements                          # absolute: root elements.py (fire)
from ..elements import create_air       # relative: alchemy/elements.py
from ..potions import strength_potion   # relative: alchemy/potions.py

This file satisfies the subject's "at least one absolute and one relative import". You also correctly predicted that from ..potions import healing_potion would be the way to get the other potion.

So what's the real difference?

  • Portability: relative imports survive renaming the package. Rename alchemy to lab and from .recipes import ... still works, but from alchemy.elements import ... breaks.
  • Clarity: an absolute import tells the reader exactly where something lives. PEP 8 recommends absolute imports as the default and accepts relative ones for imports inside the same package.
  • Brevity: relative imports are shorter, but ....module chains get hard to read quickly.
The question the subject asks: when to use which?

Absolute for clarity, for imports across different packages, and for entry-point scripts. Relative for closely related files inside the same package, especially if the package might be renamed or moved.

Gotcha to know

Relative imports only work when the file is imported as part of a package. If you run a package file directly (python3 alchemy/potions.py) you get ImportError: attempted relative import with no known parent package. That's why every test script lives at the root and imports alchemy, instead of running the package files directly.

04Circular imports

Rule #1 — the one that unlocks everything

Top-level imports execute immediately when the file is loaded

Not when you call a function. Python runs a file from line 1 downwards the moment it's imported, and an import line at the top is executed right then. Only an import inside a function waits until that function is called.

This was the one thing you had backwards early in our session, so make sure it sticks.

The crash, one step at a time (dark magic)

dark_spellbook.pyline 10
from .dark_validator import validate_ingredients
dark_validator.pyline 4
from .dark_spellbook import dark_spell_allowed_ingredients
ft_kaboom_1.py · line 14

Imports alchemy.grimoire.dark_spellbook. Python first runs alchemy/__init__.py and grimoire/__init__.py (both fine), then starts executing dark_spellbook.py and registers it in sys.modules right away, still empty.

dark_spellbook.py · line 10

First real line: import dark_validator. Python pauses dark_spellbook here and goes to load dark_validator.py.

dark_validator.py · line 4

First real line: import dark_spell_allowed_ingredients from dark_spellbook. Python finds dark_spellbook in sys.modules, but it's only partially initialized.

The name doesn't exist yet

dark_spell_allowed_ingredients is defined further down dark_spellbook.py, and Python never got past line 10. Result: ImportError: cannot import name ... from partially initialized module ... (most likely due to a circular import).

A refinement of "infinite loop"

You described it as a loop, which is a good mental picture. Technically Python doesn't spin forever: because modules are registered in sys.modules before they finish loading, the second visit finds a half-built module and fails immediately.

The fix used for light magic

light_spellbook.pyline 3
from .light_validator import validate_ingredients   # top-level: fine
light_validator.pylines 3 & 16–18
def validate_ingredients(ingredients: str) -> str:
    ...
    # Late import: executed only when this function is called
    from .light_spellbook import light_spell_allowed_ingredients

At load time, light_validator imports nothing from the spellbook, so no cycle exists. By the time validate_ingredients() is actually called, both modules are fully loaded and sitting in sys.modules, so the import inside the function just grabs the finished one.

And your answer for the dark side, which was correct: move the import inside validate_ingredients() in dark_validator.py and the explosion is defused.

Other ways to break a cycle

The subject says "there are multiple ways, be prepared to explain." You used #1. Know all three:

  1. Late (function-level) import: what you did. Simple, but hides the dependency inside the function.
  2. Restructure: move the shared piece (here, the allowed-ingredients list) into a third module that both files import. No cycle can exist when dependencies only point one way. Often the cleanest design.
  3. Import the module, not the name: write from . import dark_spellbook at the top and call dark_spellbook.dark_spell_allowed_ingredients() inside the function. The module object exists even while half-loaded, and the attribute is only looked up at call time.

The same line, caught twice (ft_alembic_4.py)

You ran mypy and got:

terminal
ft_alembic_4.py:21: error: Module has no attribute "create_earth"; maybe "create_air"?  [attr-defined]
  • mypy: reads the code without running it, sees alchemy has no create_earth, and reports it. The program is unaffected.
  • Runtime: when execution reaches line 21, Python really looks up the attribute and crashes with AttributeError.

Think of mypy as a spell-checker and the runtime error as the message actually failing to send.

flake8 rule E402 says imports belong at the top of the file. In ft_kaboom_1.py you print three lines before the import so the output matches the subject's example. That triggers E402, so the import needs a suppression.

06Evaluation Q&A — test yourself

Try to answer out loud before opening each one. Explaining in your own words is what the evaluators are checking.

What makes a folder a package?

The presence of an __init__.py file. It runs once on first import and defines what the package exposes. (Modern Python also tolerates folders without it, "namespace packages", but the subject uses the classic form.)

Why does alchemy.create_earth() fail but alchemy.create_air() work?

Only create_air is imported in alchemy/__init__.py, so only it becomes an attribute of the package. create_earth still exists in alchemy/elements.py, but it isn't re-exported.

In alchemy/potions.py, why two imports of "elements"?

There are two different files. import elements resolves through sys.path to the root file (fire, water). from .elements import ... uses the dot to mean "inside my own package," giving alchemy/elements.py (earth, air).

What is sys.path and why is it forbidden to modify?

It's the ordered list of folders Python searches for modules. The first entry is the folder of the script you ran. Editing it would let you bend import resolution instead of using proper package structure, and the exercise is about understanding that structure.

What do . and .. mean in an import?

Current package and parent package, respectively. In alchemy/transmutation/recipes.py: . is alchemy.transmutation, .. is alchemy.

Absolute or relative: which is better?

Neither always. Absolute is clearer and PEP 8's default; relative is shorter and survives package renames. Use relative for tightly coupled files in one package, absolute elsewhere.

When does a top-level import run, versus one inside a function?

Top-level: at the moment the file is first loaded. Inside a function: each time the function is called (and, thanks to sys.modules, it reuses the already-loaded module after the first load).

Explain exactly why ft_kaboom_1.py crashes.

dark_spellbook imports dark_validator on line 10 before defining anything. dark_validator immediately imports a name from dark_spellbook, which is registered but only partially initialized, so the name doesn't exist yet. Python raises ImportError mentioning a circular import.

Name three ways to avoid a circular dependency.

(1) Move the import inside the function. (2) Restructure: put shared code in a third module. (3) Import the module rather than the name and access the attribute at call time.

Why does light_validator work even though the two light files depend on each other?

The dependency is only needed when validate_ingredients() runs, not when the file loads. At load time there's no cycle; at call time everything is already loaded.

mypy error vs runtime error: what's the difference?

mypy analyses code without running it and reports problems beforehand without stopping anything. A runtime error happens during execution and stops the program at that line.

Why noqa: F401 in __init__.py?

The imports are only there to re-export names, so flake8 sees them as "imported but unused." The comment silences that false alarm. __all__ is the other standard way to declare the intent.

What would you change to make healing_potion available as alchemy.healing_potion too?

Add from alchemy.potions import healing_potion # noqa: F401 to alchemy/__init__.py. An evaluator may ask you to modify the lab live, so practice small edits like this.

08Cheat sheet

  1. Folder + __init__.py = package. The file decides what's visible from outside.
  2. Bare import X searches sys.path, which starts at the folder of the script you ran.
  3. . = this package, .. = parent package.
  4. Top-level imports run at load time. Imports inside functions run at call time.
  5. Modules are registered in sys.modules as soon as loading starts. A second import mid-load sees a half-built module.
  6. Cycle fixes: late import, restructure into a third module, import the module instead of the name.
  7. mypy and flake8 run before execution; runtime errors happen during it.
  8. Before the defense: run flake8 and mypy on everything, run all 13 scripts, and be able to explain every import line out loud.
