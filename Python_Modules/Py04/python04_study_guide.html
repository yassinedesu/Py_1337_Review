Core thread

A file is a resource owned by the operating system. You must acquire it, use it, and release it, even when something fails halfway. Every concept below serves that single idea.

02

File objects & open()

The most common misconception

open() does not return the file's contents and it never returns None on failure. It returns a file object, a handle to the file. If it fails, it raises an exception.

open("f.txt")returns a handle
→
file.read()returns a str
→
file.close()releases the OS resource
file = open("f.txt")     # file object (io.TextIOWrapper)
content = file.read()    # str: the actual text
file.close()             # give the handle back to the OS

What type is it, exactly?

  • In text mode the concrete type is io.TextIOWrapper.
  • typing.IO[str] is an abstract type hint for "any text file-like object". TextIOWrapper satisfies it, so it is a correct and idiomatic annotation.
  • In binary mode ("rb") the object is a BufferedReader and read() returns bytes, not str.

Useful methods

MethodDoes
read()Entire remaining content as one string
readline()One line, including its trailing \n; returns "" at end of file
write(s)Writes a string; returns the number of characters written
flush()Pushes buffered data out immediately
close()Flushes, then releases the OS file descriptor

Modes & encoding

When you call open("f") with no arguments, you get mode "r" (read, text) and an encoding taken from the system locale (usually UTF-8, but not guaranteed).

ModeMeaningIf file missingIf file exists
"r"Read text (default)FileNotFoundErrorOpens at the start
"w"Write textCreates itErases content immediately
"a"Append textCreates itWrites at the end
"x"Exclusive createCreates itFileExistsError
"b"Binary flag, e.g. "rb"Gives bytes instead of str
Be aware

"w" truncates the file the moment open() succeeds, before you write anything. That is why exercise 1 says "create the file or replace it if it already exists".

Explicit encoding

open("f.txt", encoding="utf-8")   # portable across machines
04

Exceptions in file I/O

File operations fail for many reasons. Python groups them in a hierarchy, and knowing the tree tells you what your except clause really catches.

Exception ├── OSError # OS-level failures │ ├── FileNotFoundError # [Errno 2] No such file or directory │ ├── PermissionError # [Errno 13] Permission denied │ ├── IsADirectoryError # tried to open a directory as a file │ └── FileExistsError # mode "x" on an existing file └── ValueError └── UnicodeDecodeError # NOT an OSError: bytes can't be decoded as text
The trap

except OSError does not catch everything. Reading a binary file (an image, a compiled program) in text mode raises UnicodeDecodeError. open() succeeds, read() blows up, and your except OSError never sees it.

try / except / else / finally

BlockRuns when
tryAlways first
except XThe try block raised an exception matching X
elseThe try block raised nothing
finallyAlways, even on return or an uncaught exception

The error message in your output ([Errno 2] No such file or directory: 'foo') is simply str(e) of the caught exception.

05

Resource leaks & the None pattern

Why initialize file to None?

file: typing.IO[str] | None = None
try:
    file = open(filename)      # if THIS raises, file keeps its None value
    content = file.read()
except OSError as e:
    ...
finally:
    if file is not None:       # safe: only close what was actually opened
        file.close()

Without the pre-initialization, a failing open() leaves file undefined, and any later reference to it raises NameError (more precisely UnboundLocalError inside a function). The | None in the annotation tells mypy that the variable may legitimately be empty.

In your ex0–ex2

Because you return inside the except, file.close() is only reached after a successful open, so the None initialization is technically redundant there. It becomes essential the moment you use a finally block.

Where your ex0–ex2 still leak

try:
    file = open(filename)          # succeeds, handle is now open
    print(file.read(), end="")     # UnicodeDecodeError raised here
except OSError as e:               # wrong exception type, not caught
    ...
file.close()                       # never reached, handle leaks

The fix without with (allowed in ex0–ex2)

The subject forbids with until exercise 3, so the correct older pattern is try/except/finally:

def read_file(filename: str) -> str | None:
    file: typing.IO[str] | None = None
    try:
        file = open(filename)
        content: str = file.read()
    except (OSError, ValueError) as e:        # ValueError covers UnicodeDecodeError
        sys.stderr.write(f"[STDERR] Error opening file '{filename}': {e}\n")
        return None
    finally:
        if file is not None:
            file.close()
            print(f"File '{filename}' closed.")
    return content
06

Context managers & with

The with statement works through a protocol made of two special methods. It isn't magic: any object that defines them can be used in a with.

__enter__(self)

Runs when the block is entered. Its return value is what as name binds. For files it returns the file object itself.

__exit__(self, exc_type, exc, tb)

Runs when the block ends for any reason: normal end, return, break, or an exception. For files it calls close().

What it really expands to

with open("f.txt") as file:
    content = file.read()

# is roughly equivalent to:
file = open("f.txt")
try:
    content = file.read()
finally:
    file.close()          # __exit__ does this, always
The single most important takeaway

with gives a guarantee: the cleanup runs no matter how the block exits. A plain try/except only protects against the exception types you listed; with (like finally) protects against all of them.

Subtle points

  • A return inside a with block still triggers __exit__, which is why your ex3 can return (True, file.read()) safely.
  • with does not swallow exceptions by itself. If open() fails or read() raises, the exception still propagates after the file is closed, so you still need try/except around it.
  • If open() itself fails, there is no file to close, so __exit__ is never called. That is why with needs no None initialization.
07

stdin, stdout, stderr

Every process starts with three open streams. They are file objects too, which is why sys.stdout.write() and file.write() look identical.

StreamfdPythonPurpose
Standard input0sys.stdinData coming in (keyboard or a pipe)
Standard output1sys.stdoutNormal results
Standard error2sys.stderrDiagnostics and errors

Why separate stdout and stderr?

In a plain terminal they look the same. The difference appears when the user redirects:

python3 prog.py foo  > out.txt        # stdout to file, errors STILL show on screen
python3 prog.py foo 2> err.txt        # errors to file, results stay on screen
python3 prog.py foo  > out.txt 2>&1   # both into the same file

Errors that vanish silently into an output file would be dangerous, and results mixed with error text would corrupt anything piped into another program.

Reading input without input()

def get_user_input(prompt: str) -> str:
    sys.stdout.write(prompt)
    sys.stdout.flush()
    return sys.stdin.readline().rstrip("\n")
  • sys.stdin.readline() keeps the trailing \n, so you strip it. rstrip("\n") is more precise than strip(), which would also eat meaningful leading or trailing spaces in a file name.
  • At end of input (Ctrl-D) readline() returns "", which your code treats as "empty, don't save".

Buffering and flush()

Python does not send every character to the screen instantly. Output waits in a buffer and is sent in chunks. On a terminal, stdout is line-buffered: the buffer is emptied when a newline is written.

Why your prompt needs flush

A prompt like "Enter new file name (or empty): " has no trailing newline, so it can sit in the buffer while readline() already waits for the user, who sees nothing. flush() forces it out first. The built-in input() flushes for you; sys.stdout.write() does not.

stderr is unbuffered or line-buffered by design, so error messages appear immediately.

08

Transforming text & the splitlines() trap

"a\nb\nc\n".splitlines()   # ['a', 'b', 'c']        trailing \n is dropped
"a\nb\nc\n".split("\n")   # ['a', 'b', 'c', '']    leaves an empty last item

Your transform_content joins the lines back with "\n", so a file that ended with a newline loses it:

"\n".join(l + "#" for l in "a\nb\n".splitlines())
# 'a#\nb#'          <- no final newline, differs from the original
Fix
def transform_content(content: str) -> str:
    result: str = "\n".join(line + "#" for line in content.splitlines())
    if content.endswith("\n"):
        result += "\n"
    return result
Know the difference

splitlines() understands \n, \r\n and \r. split("\n") only understands \n. Pick on purpose.

ex2: Stream Management

  • Errors go to sys.stderr with the [STDERR] prefix.
  • Input comes from sys.stdin.readline(), prompt written with sys.stdout.write() plus flush().
  • On a failed save, also print Data not saved. (stdout).

ex3: Vault Security

A reusable function that never raises and always returns (success, text):

ALLOWED_MODES: set[str] = {"r", "w"}


def secure_archive(
    filename: str, mode: str = "r", content: str = ""
) -> tuple[bool, str]:
    """Read or write a file safely. Returns (ok, content_or_error)."""
    if mode not in ALLOWED_MODES:
        return (False, f"Invalid mode '{mode}': use 'r' or 'w'")
    try:
        with open(filename, mode) as file:
            if mode == "r":
                return (True, file.read())
            file.write(content)
            return (True, "Content successfully written to file")
    except (OSError, ValueError) as e:
        return (False, str(e))
Why two changes from your version

Mode validation: without it, "rb" would make read() return bytes, breaking the tuple[bool, str] promise, and "x" or "a" would behave unexpectedly. Catching ValueError too: your function promises it never raises, but reading a binary file would raise UnicodeDecodeError straight through except OSError. The file would still be closed by with, but the caller would crash.

10

Python quirks from your code

end=None is not "no newline"

None means "use the default", and the default is "\n".

print("hi", end=None)  # hi + newline
print("hi", end="")    # hi, no newline

Implicit string concatenation

Adjacent literals are joined at compile time.

"" "to write"      # 'to write'
"Hello" " world"   # 'Hello world'

Harmless in your ex3, but the leading "" is dead code.

Corrections & pitfalls

Correction to something said earlier in our session

I previously said print() flushes automatically while sys.stdout.write() does not. That was imprecise. print() has flush=False by default; it only appears to flush on a terminal because its trailing newline triggers line-buffering. The built-in input() is the one that flushes the prompt. The practical advice stands: when you write a prompt without a newline, call flush().

MisconceptionReality
open() returns the file content or NoneIt returns a file object, or raises an exception
OSError catches every file problemDecoding errors are ValueError subclasses
stdout and stderr are the same thingSame terminal, but independent under redirection
end=None removes the newlineOnly end="" does
splitlines() keeps the final newlineIt silently drops it
with catches exceptionsIt only guarantees cleanup; the exception still propagates
Initializing file = None is "just a type hint"It is a real assignment that keeps the name defined
12

Defense Q&A

Click each question and try to answer out loud before opening it.

What does open() return, and what happens on failure?

A file object (io.TextIOWrapper in text mode). On failure it raises an OSError subclass such as FileNotFoundError or PermissionError. It never returns None.

Why can a file leak even if you wrote try/except?

Because except only handles the exception types listed. If read() raises something else (e.g. UnicodeDecodeError), the code after the try/except, including close(), is skipped. A finally block or with closes regardless.

What are __enter__ and __exit__?

The context manager protocol. __enter__ runs on entering the with block and supplies the as value. __exit__ runs on leaving it, whether normally, via return, or through an exception. For files it closes the handle.

Why initialize file to None before the try?

So the name exists even if open() fails, allowing a safe if file is not None: file.close() in finally. Without it you could hit a NameError.

Why write errors to stderr?

So they stay visible and separate when stdout is redirected or piped. Results and diagnostics are different data streams.

Why call sys.stdout.flush() after writing a prompt?

The prompt has no newline, so line-buffered stdout may hold it back while the program already waits on stdin. Flushing guarantees the user sees it first.

What does mode "w" do to an existing file?

It truncates it to zero length as soon as the file is opened. If the file does not exist it is created.

Why validate the mode in secure_archive()?

To keep the contract: the function must return tuple[bool, str]. Binary modes would yield bytes; "x"/"a" have behaviours the function wasn't designed for.

Does with handle exceptions for you?

No. It guarantees cleanup, then lets the exception continue upward. You still wrap it in try/except to turn failures into (False, message).

What does splitlines() do with a trailing newline, and why does it matter?

It drops it. Re-joining with "\n" therefore yields a file without the original final newline, so you must add it back if the input had one.
