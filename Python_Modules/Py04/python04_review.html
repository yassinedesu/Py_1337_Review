What You Got Wrong
Concept open() does NOT return a string

You initially said open() returns the file content as a string or None. This is a fundamental mix-up. open() returns a file object — a handle to the file resource. The string comes later when you call .read() on it.

# open() → file object (the door handle)
file = open("foo.txt") # TextIOWrapper object
content = file.read() # NOW you get the str
file.close()
ex1/ex2 Trailing newline lost in transform_content()

splitlines() silently discards the trailing newline that most text files end with. Your "\n".join(...) then produces a file without a final newline — a silent difference from the original.

"line1\nline2\n".splitlines()
# → ["line1", "line2"] ← trailing \n is GONE

# Fix: preserve it explicitly
result = "\n".join(l + "#" for l in content.splitlines())
if content.endswith("\n"):
    result += "\n"
ex3 end=None is not what you think

You thought end=None suppresses the newline. It doesn't — None is Python's sentinel for "use the default", and the default is "\n". You meant end="".

print("hello", end=None) # → "hello\n" (newline IS printed)
print("hello", end="") # → "hello" (no newline)
Concept OSError does not catch everything

You thought OSError covered all failure cases. It only handles OS-level errors (missing file, permissions). A UnicodeDecodeError (reading a binary file in text mode) is a ValueError subclass — it escapes your except block completely, and the file handle leaks.

ex2 sys.stdout.flush() purpose unclear

Python buffers stdout for efficiency — output sits in memory and is flushed in batches. Without flush() before reading from stdin, the prompt may never appear on screen before your program starts waiting for input. print() does this automatically; sys.stdout.write() does not.

Things to Review & Be Aware Of
Review typing.IO[str] vs TextIOWrapper

The real concrete type returned by open() in text mode is io.TextIOWrapper. typing.IO[str] is an abstract interface that TextIOWrapper satisfies — it's the idiomatic type hint for "any text file-like object". Both are correct but for different reasons.

Review The finally block vs with

Before context managers existed, the pattern was try/finally. Understanding this helps you grasp why with was invented — it's syntactic sugar for a try/finally that always closes the resource, even on any uncaught exception.

# Equivalent to: with open("f") as file
file = open("f")
try:
    content = file.read()
finally:
    file.close() # always runs
Aware Implicit string concatenation

Two string literals written next to each other are joined at compile time: "hello" " world" → "hello world". It's a Python quirk, useful for breaking long strings across lines, but easy to introduce silently by accident.

Aware Default open() mode & encoding

When you call open("file") with no arguments, the defaults are mode "r" (text read) and encoding from locale.getpreferredencoding() — usually UTF-8 on modern systems, but not guaranteed. For portability, be explicit: open("file", encoding="utf-8").

Aware splitlines() vs split("\n")

splitlines() handles all line ending styles (\n, \r\n, \r) and discards the trailing newline. split("\n") only handles Unix newlines and produces a trailing empty string. Know which behavior you need before picking one.
