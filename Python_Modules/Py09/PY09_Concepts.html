1. Subject rules & tooling

These come from the "General Instructions" chapter. They are graded, so they count as much as the Pydantic itself.

Python and environment

  • Python 3.10 or later. 3.10 added the X | None union syntax and better error messages.
  • pip + a virtual environment (venv, virtualenv or conda). A virtual environment is an isolated folder of installed packages, so this project's Pydantic version cannot collide with another project's.
  • Pydantic 2.x only, installed with pip. Pydantic 1 has a different API; most online tutorials you find may still show v1 code.
  • Only standard-library modules are allowed besides Pydantic. Each exercise lists Authorized: None, which means no extra imports beyond Pydantic and the standard library.
python3 -m venv .venv
source .venv/bin/activate
pip install pydantic flake8 mypy

flake8 (code style)

flake8 is a linter: a program that reads your code without running it and reports style problems and likely bugs. The classic ones:

  • E501: line longer than 79 characters. This is the one that bit us.
  • F401: imported but unused.
  • E302 / E305: need two blank lines around top-level functions and classes.
  • W291 / W293: trailing whitespace.

Run it with flake8 ex0 ex1 ex2. No output means no problems.

mypy (type checking)

mypy reads your type hints and checks that they are consistent, without running the code. If you declare def f(x: int) -> str and then return an int, mypy complains. The subject requires "comprehensive type annotations": every parameter, every return value, and (in our solutions) local variables too.

Exception handling

"Exception handling should protect the data streams from corruption." In this module that means: invalid data is caught with try / except ValidationError and reported, instead of crashing the program or silently getting through.

Docstrings and comments

The subject asks for clear comments and meaningful names. The correction sheet states docstrings are not required for this module, but they are still good practice, and type hints on every function are required.

2. Why Pydantic exists

Python type hints are only documentation at runtime. This runs happily:

class Station:
    crew_size: int = 0

s = Station()
s.crew_size = "banana"   # Python does not care
s.crew_size = -500       # Python does not care

Data coming from outside your program (an API, a JSON file, a CSV, a form) is exactly where garbage arrives. Pydantic turns type hints into enforced rules: when you build an object, every value is checked and converted. If anything is wrong you get a precise error, and you never end up holding a half-valid object.

Analogy: the customs officer

Your model is a customs form. Pydantic is the officer who checks every box before letting the data into the country (your program). Inside the country, you can trust the data completely, because nothing unchecked ever crossed the border.

"Parse, don't just validate"

Pydantic does two jobs in one step: it checks the data and it converts it into the right Python type. You hand it the string "2024-01-15T10:30:00" and get back a real datetime. That is why the subject's tip says it "automatically converts compatible types".

3. Exercise 0: Space Station Data

Objective Learn basic Pydantic model creation with BaseModel and Field validation.

3.1 BaseModel

What it is

The class every Pydantic model inherits from. You declare fields as annotated class attributes, and Pydantic generates an __init__ that validates them.

How it works

  1. When Python defines your class, Pydantic reads the annotations (crew_size: int) and builds a schema (a validation plan) for each field.
  2. When you call SpaceStation(crew_size=6, ...), the values are passed through that plan field by field.
  3. If all pass, you get an object with typed attributes. If any fail, no object is created and a ValidationError is raised.
from pydantic import BaseModel

class Point(BaseModel):
    x: int
    y: int

p = Point(x=1, y="2")   # "2" is converted to 2
print(p.y + 1)          # 3, a real int
Point(x=1, y="abc")     # ValidationError

Things to remember

  • Models are created with keyword arguments: Point(x=1), not Point(1).
  • You access validated data as attributes: station.crew_size.
  • A field with only an annotation and no default is required.

3.2 Field() and constraints

What it is

Field(...) attaches rules and metadata to one attribute. It answers "what values are acceptable?" beyond just the type.

The constraint parameters used in this module

Common mistake

Using min_length on a number or ge on a string. Rule of thumb: numbers use ge / le / gt / lt; strings and lists use min_length / max_length. The names min and max do not exist.

3.3 Required vs default: the ... (Ellipsis)

The first argument of Field is the default value. Passing ... (the literal Python Ellipsis) is a convention that means "no default, this field is required".

crew_size: int = Field(..., ge=1, le=20)   # required
is_operational: bool = Field(default=True)  # optional, defaults to True

In Pydantic v2, Field(ge=1) without a default is also required, but writing ... makes the intent obvious to a reader and is the style the subject follows.

3.4 Optional fields

Optional[str] means "a string or None". It is exactly the same as str | None (the 3.10+ spelling).

Optional does not mean "can be omitted"

Optional[str] only says None is an allowed value. To also let the caller leave it out entirely, give it a default: Optional[str] = Field(default=None, ...). That combination is what notes uses.

Constraints such as max_length=200 apply only when a string is actually provided; None skips them.

3.5 datetime and automatic type coercion

A field annotated datetime accepts a real datetime object or a string in ISO 8601 format, and converts it:

from datetime import datetime
from pydantic import BaseModel

class Event(BaseModel):
    when: datetime

e = Event(when="2024-01-15T10:30:00")
print(type(e.when))   # <class 'datetime.datetime'>
print(e.when.year)    # 2024

The subject's "Think About" question, answered

"What happens when you pass a string timestamp to a datetime field?" Pydantic parses the string and builds a datetime. If the string is not a valid date ("hello", "2024-13-45"), validation fails with a clear error.

How far does coercion go?

By default Pydantic is in lax mode: it converts sensible things ("42" to 42, "true" to True, an ISO string to a datetime) but still rejects nonsense ("abc" as an int). There is also a strict mode (no conversion) which is beyond this module but a good research topic.

Why # type: ignore[arg-type] in our solutions?

At runtime passing a string is fine. But mypy reads the annotation last_maintenance: datetime and thinks a str is a type error. The comment tells mypy "I know, ignore this one line". Alternative: pass datetime(2024, 1, 15, 10, 30) and no ignore is needed.

3.6 ValidationError

What it is

The exception Pydantic raises when validation fails. It lives in pydantic and is a subclass of ValueError.

Why it is better than a normal exception

It collects all problems, not just the first. Each problem is a dictionary you can inspect with error.errors():

try:
    SpaceStation(station_id="X", name="", crew_size=25, ...)
except ValidationError as error:
    for problem in error.errors():
        print(problem["loc"], problem["msg"], problem["type"])
KeyContainsExample
locpath to the failing field('crew_size',)
msghuman-readable messageInput should be less than or equal to 20
typemachine-readable error codeless_than_equal
inputthe offending value25

The expected output in the subject, Input should be less than or equal to 20, is exactly error.errors()[0]["msg"]. Printing the whole error object would show a much longer multi-line report.

3.8 Solution: ex0/space_station.py

#!/usr/bin/env python3
"""Exercise 0: Space Station Data Validation."""

from datetime import datetime
from typing import Optional

from pydantic import BaseModel, Field, ValidationError


class SpaceStation(BaseModel):
    """A monitored space station with validated telemetry."""

    station_id: str = Field(..., min_length=3, max_length=10)
    name: str = Field(..., min_length=1, max_length=50)
    crew_size: int = Field(..., ge=1, le=20)
    power_level: float = Field(..., ge=0.0, le=100.0)
    oxygen_level: float = Field(..., ge=0.0, le=100.0)
    last_maintenance: datetime = Field(...)
    is_operational: bool = Field(default=True)
    notes: Optional[str] = Field(default=None, max_length=200)


def display_station(station: SpaceStation) -> None:
    """Print the station information in a readable format."""
    status_label: str = "Operational" if station.is_operational else "Offline"
    print(f"ID: {station.station_id}")
    print(f"Name: {station.name}")
    print(f"Crew: {station.crew_size} people")
    print(f"Power: {station.power_level}%")
    print(f"Oxygen: {station.oxygen_level}%")
    print(f"Status: {status_label}")
    if station.notes:
        print(f"Notes: {station.notes}")


def main() -> None:
    """Show one valid station and one invalid station."""
    print("Space Station Data Validation")
    print("=" * 40)

    valid_station: SpaceStation = SpaceStation(
        station_id="ISS001",
        name="International Space Station",
        crew_size=6,
        power_level=85.5,
        oxygen_level=92.3,
        last_maintenance="2024-01-15T10:30:00",  # type: ignore[arg-type]
        is_operational=True,
        notes="All systems nominal",
    )
    print("Valid station created:")
    display_station(valid_station)
    print("=" * 40)

    print("Expected validation error:")
    try:
        SpaceStation(
            station_id="BAD001",
            name="Overcrowded Station",
            crew_size=25,  # invalid: maximum is 20
            power_level=80.0,
            oxygen_level=90.0,
            last_maintenance="2024-01-15T10:30:00",  # type: ignore[arg-type]
        )
    except ValidationError as error:
        print(error.errors()[0]["msg"])


if __name__ == "__main__":
    main()

4. Exercise 1: Alien Contact Logs

Objective Master custom validation using @model_validator for complex business rules.

New concepts here: Enum and @model_validator(mode="after"). Everything from Exercise 0 (BaseModel, Field, Optional, ValidationError) is reused.

4.1 Enum

What it is

A class that defines a closed list of allowed values, each with a name.

from enum import Enum

class ContactType(Enum):
    RADIO = "radio"
    VISUAL = "visual"
    PHYSICAL = "physical"
    TELEPATHIC = "telepathic"

The problem it solves

With a plain str field, "radio", "Radio", "raido" and "banana" are all accepted. With an Enum field, only the four listed values pass. It also prevents typos in your own code: ContactType.RADIOO fails immediately.

How it works with Pydantic

  • Input can be the member itself (ContactType.RADIO) or its value ("radio"). Pydantic converts the string into the member. This is what makes loading JSON data work.
  • Each member has .name ("RADIO") and .value ("radio"). The expected output prints radio, so use .value.
  • Compare with members, not strings: contact.contact_type == ContactType.PHYSICAL. Comparing to "physical" is always False.
Analogy

A dropdown menu instead of a free text box.

4.2 @model_validator(mode="after")

The problem

Field() constraints look at one field in isolation. But the business rules in this exercise compare fields with each other:

  • "If contact_type is physical, then is_verified must be true" (two fields)
  • "If contact_type is telepathic, then witness_count must be at least 3" (two fields)
  • "If signal_strength > 7.0, then message_received must exist" (two fields)

No single-field constraint can express these.

How it works

  1. Pydantic validates every field first (types, Field constraints).
  2. If all fields passed, it builds the object and calls your decorated method, passing the finished object as self.
  3. You inspect any attributes you want. To reject, raise ValueError("message"). To accept, return self.
  4. Pydantic wraps your ValueError into a ValidationError for the caller.
@model_validator(mode="after")
def apply_business_rules(self) -> "AlienContact":
    if self.contact_type == ContactType.PHYSICAL and not self.is_verified:
        raise ValueError("Physical contact reports must be verified")
    return self

mode="after" vs mode="before"

mode="after" (this module)mode="before"
RunsAfter all fields are validatedBefore any field validation
What self / input isA real model instance with typed attributesThe raw input (usually a dict)
Typical useCross-field business rulesReshaping or cleaning raw input

Consequence: if a field fails its own constraint (say signal_strength=15), the "after" validator never runs, because there is no valid object to inspect.

Why the return type is the string "AlienContact"

Inside the class body, the name AlienContact does not exist yet, so the annotation is written as a string (a forward reference). mypy understands it.

Pydantic v1 vs v2 (the subject warns about this)

Pydantic v1 (deprecated, forbidden)Pydantic v2 (required)
@validator("field")@field_validator("field") for one field, or @model_validator for whole-model rules
@root_validator@model_validator
Receives cls, value, valuesmode="after" receives self

Common mistakes

  • Forgetting return self. The model would come back as None.
  • Raising Exception instead of ValueError (or AssertionError). Only those become a clean ValidationError.
  • Using the deprecated @validator. The correction sheet explicitly checks this.
  • Writing the condition wrongly (see the bug in section 9).

The four business rules

RuleCheck
Contact ID starts with "AC"self.contact_id.startswith("AC")
Physical contacts must be verifiedcontact_type == PHYSICAL and not is_verified is an error
Telepathic needs 3+ witnessescontact_type == TELEPATHIC and witness_count < 3 is an error
Strong signal (> 7.0) needs a messagesignal_strength > 7.0 and message_received is None is an error

Notice the pattern: each rule is written as "the bad situation", and when it is true, we raise. Think of it as describing what is wrong, not what is right.

4.3 The "Value error, " prefix

When your validator raises ValueError("Telepathic contact requires at least 3 witnesses"), Pydantic stores the message as:

Value error, Telepathic contact requires at least 3 witnesses

The expected output in the subject shows the message without that prefix, so the demonstration strips it:

raw_msg: str = error.errors()[0]["msg"]
prefix: str = "Value error, "
if raw_msg.startswith(prefix):
    clean_message: str = raw_msg[len(prefix):]
else:
    clean_message = raw_msg
print(clean_message)

raw_msg[len(prefix):] is string slicing: take everything from index len(prefix) to the end, which removes the first 13 characters.

4.4 Solution: ex1/alien_contact.py

#!/usr/bin/env python3
"""Exercise 1: Alien Contact Log Validation."""

from datetime import datetime
from enum import Enum
from typing import Optional

from pydantic import BaseModel, Field, ValidationError, model_validator


class ContactType(Enum):
    """Recognised alien contact categories."""

    RADIO = "radio"
    VISUAL = "visual"
    PHYSICAL = "physical"
    TELEPATHIC = "telepathic"


class AlienContact(BaseModel):
    """A single alien contact report."""

    contact_id: str = Field(..., min_length=5, max_length=15)
    timestamp: datetime = Field(...)
    location: str = Field(..., min_length=3, max_length=100)
    contact_type: ContactType = Field(...)
    signal_strength: float = Field(..., ge=0.0, le=10.0)
    duration_minutes: int = Field(..., ge=1, le=1440)
    witness_count: int = Field(..., ge=1, le=100)
    message_received: Optional[str] = Field(default=None, max_length=500)
    is_verified: bool = Field(default=False)

    @model_validator(mode="after")
    def apply_business_rules(self) -> "AlienContact":
        """Check the cross-field business rules; return self if valid."""
        if not self.contact_id.startswith("AC"):
            raise ValueError(
                "Contact ID must start with 'AC' (Alien Contact)"
            )

        if self.contact_type == ContactType.PHYSICAL and not self.is_verified:
            raise ValueError("Physical contact reports must be verified")

        if (
            self.contact_type == ContactType.TELEPATHIC
            and self.witness_count < 3
        ):
            raise ValueError(
                "Telepathic contact requires at least 3 witnesses"
            )

        if self.signal_strength > 7.0 and self.message_received is None:
            raise ValueError(
                "Strong signal (> 7.0) should include a received message"
            )

        return self


def display_contact(contact: AlienContact) -> None:
    """Print the contact report in a readable format."""
    print(f"ID: {contact.contact_id}")
    print(f"Type: {contact.contact_type.value}")
    print(f"Location: {contact.location}")
    print(f"Signal: {contact.signal_strength}/10")
    print(f"Duration: {contact.duration_minutes} minutes")
    print(f"Witnesses: {contact.witness_count}")
    if contact.message_received:
        print(f"Message: '{contact.message_received}'")


def main() -> None:
    """Show one valid contact report and one invalid one."""
    print("Alien Contact Log Validation")
    print("=" * 38)

    valid_contact: AlienContact = AlienContact(
        contact_id="AC_2024_001",
        timestamp="2024-01-15T14:30:00",  # type: ignore[arg-type]
        location="Area 51, Nevada",
        contact_type=ContactType.RADIO,
        signal_strength=8.5,
        duration_minutes=45,
        witness_count=5,
        message_received="Greetings from Zeta Reticuli",
        is_verified=False,
    )
    print("Valid contact report:")
    display_contact(valid_contact)
    print("=" * 38)

    print("Expected validation error:")
    try:
        AlienContact(
            contact_id="AC_2024_002",
            timestamp="2024-01-16T09:15:00",  # type: ignore[arg-type]
            location="Roswell, New Mexico",
            contact_type=ContactType.TELEPATHIC,
            signal_strength=6.2,
            duration_minutes=30,
            witness_count=1,  # invalid: telepathic needs 3 or more
            is_verified=False,
        )
    except ValidationError as error:
        raw_msg: str = error.errors()[0]["msg"]
        prefix: str = "Value error, "
        if raw_msg.startswith(prefix):
            clean_message: str = raw_msg[len(prefix):]
        else:
            clean_message = raw_msg
        print(clean_message)


if __name__ == "__main__":
    main()

5. Exercise 2: Space Crew Management

Objective Master nested Pydantic models and complex data relationships.

New concepts: nested models, lists of models, list length constraints, and the validation cascade. A second Enum (Rank) reuses what you learned in Exercise 1.

5.1 Nested models

What it is

Using one model as the type of a field in another model.

class CrewMember(BaseModel):
    name: str
    rank: Rank

class SpaceMission(BaseModel):
    mission_id: str
    crew: List[CrewMember]   # a list of CrewMember models

The problem it solves

Real data is a tree, not a flat table: a mission has crew members, each with their own rules. Nesting lets one call validate the entire tree.

Two ways to feed it data

# 1. Already-built objects (what our solution does)
mission = SpaceMission(crew=[sarah, john], ...)

# 2. Raw dictionaries (e.g. straight from JSON). Pydantic builds the CrewMember for you
mission = SpaceMission(crew=[{"member_id": "CM001", "name": "Sarah Connor", ...}], ...)
Analogy: Russian dolls

Before the outer doll can be closed, every inner doll must be complete and intact.

5.2 List fields and length limits

List[CrewMember] says "a list whose every element is a valid CrewMember". On Python 3.9+ you may also write list[CrewMember] (lowercase), which is equivalent.

crew: List[CrewMember] = Field(..., min_length=1, max_length=12)

Here min_length and max_length limit how many items the list has (1 to 12), exactly like they limit characters in a string. This also means you do not need to check "is the crew empty?" in your validator, because the Field already rejected it.

5.3 The validation cascade

This answers the subject's question: "What happens when a CrewMember fails validation within a SpaceMission?"

  1. Pydantic validates the simple fields of SpaceMission.
  2. For crew, it validates each element against CrewMember, including that model's own constraints.
  3. If any crew member is invalid, SpaceMission fails with a ValidationError whose loc points at the exact spot, for example ('crew', 1, 'age') meaning "second crew member, field age".
  4. Only if everything above passed does your @model_validator run.
SpaceMission(crew=[{"member_id": "CM1", "name": "A", ...}], ...)
# ValidationError: crew.0.name  String should have at least 2 characters

So the mission-level rules can safely assume every crew member is individually valid.

5.4 The four mission rules, explained

Rule 1: Mission ID starts with "M"

Same startswith pattern as Exercise 1.

Rule 2: At least one Commander or Captain

high_ranking_roles = {Rank.CAPTAIN, Rank.COMMANDER}
has_senior_officer: bool = any(
    member.rank in high_ranking_roles for member in self.crew
)
if not has_senior_officer:
    raise ValueError("Mission must have at least one Commander or Captain")
  • The {...} is a set; x in some_set is a fast membership test.
  • any(...) returns True as soon as one element satisfies the condition.
  • (member.rank in ... for member in self.crew) is a generator expression: a lazy loop that produces one boolean per crew member.

Rule 3: Long missions (> 365 days) need 50% experienced crew (5+ years)

if self.duration_days > 365:
    experienced_count: int = sum(
        1 for member in self.crew if member.years_experience >= 5
    )
    required_count: int = len(self.crew) // 2
    if experienced_count < required_count:
        raise ValueError("...")
  • sum(1 for ... if ...) is the idiom for counting elements that match a condition.
  • // is integer (floor) division. With 3 crew, 3 // 2 = 1, so 1 experienced member is required.
Know your rounding

"50%" of 3 people is 1.5. Floor division requires 1; rounding up would require 2. Our solution uses floor division, which is what makes the subject's example (Sarah 18 yrs, John 10 yrs, Alice 6 yrs, all experienced anyway) pass. Be ready to explain this choice in defense. A stricter alternative is experienced_count * 2 < len(self.crew), which means "less than half".

Rule 4: All crew members must be active

inactive_names: List[str] = [
    member.name for member in self.crew if not member.is_active
]
if inactive_names:
    raise ValueError(f"Inactive crew members cannot be assigned: {', '.join(inactive_names)}")
  • A list comprehension collects the names of inactive members.
  • An empty list is falsy, so if inactive_names: is true only when at least one name was found.
  • ', '.join(names) glues the names into one readable string.

Order of rules matters for the demo

The validator stops at the first raise. The subject's invalid example must show Mission must have at least one Commander or Captain, so that mission must pass rule 1 and fail on rule 2 (a short mission with a lone cadet does exactly that).

5.5 Solution: ex2/space_crew.py

#!/usr/bin/env python3
"""Exercise 2: Space Crew Management Validation."""

from datetime import datetime
from enum import Enum
from typing import List

from pydantic import BaseModel, Field, ValidationError, model_validator


class Rank(Enum):
    """Official crew ranks."""

    CADET = "cadet"
    OFFICER = "officer"
    LIEUTENANT = "lieutenant"
    CAPTAIN = "captain"
    COMMANDER = "commander"


class CrewMember(BaseModel):
    """A single crew member (nested inside SpaceMission)."""

    member_id: str = Field(..., min_length=3, max_length=10)
    name: str = Field(..., min_length=2, max_length=50)
    rank: Rank = Field(...)
    age: int = Field(..., ge=18, le=80)
    specialization: str = Field(..., min_length=3, max_length=30)
    years_experience: int = Field(..., ge=0, le=50)
    is_active: bool = Field(default=True)


class SpaceMission(BaseModel):
    """A mission with its crew; applies safety rules to the whole team."""

    mission_id: str = Field(..., min_length=5, max_length=15)
    mission_name: str = Field(..., min_length=3, max_length=100)
    destination: str = Field(..., min_length=3, max_length=50)
    launch_date: datetime = Field(...)
    duration_days: int = Field(..., ge=1, le=3650)
    crew: List[CrewMember] = Field(..., min_length=1, max_length=12)
    mission_status: str = Field(default="planned")
    budget_millions: float = Field(..., ge=1.0, le=10000.0)

    @model_validator(mode="after")
    def apply_safety_requirements(self) -> "SpaceMission":
        """Check the mission safety rules; return self if all pass."""
        # Rule 1: mission ID prefix
        if not self.mission_id.startswith("M"):
            raise ValueError("Mission ID must start with 'M'")

        # Rule 2: at least one Captain or Commander
        high_ranking_roles = {Rank.CAPTAIN, Rank.COMMANDER}
        has_senior_officer: bool = any(
            member.rank in high_ranking_roles for member in self.crew
        )
        if not has_senior_officer:
            raise ValueError(
                "Mission must have at least one Commander or Captain"
            )

        # Rule 3: long missions need experienced crew
        if self.duration_days > 365:
            experienced_count: int = sum(
                1 for member in self.crew if member.years_experience >= 5
            )
            required_count: int = len(self.crew) // 2
            if experienced_count < required_count:
                raise ValueError(
                    "Long missions (> 365 days) require at least 50% "
                    "of crew to have 5+ years of experience"
                )

        # Rule 4: every crew member must be active
        inactive_names: List[str] = [
            member.name for member in self.crew if not member.is_active
        ]
        if inactive_names:
            raise ValueError(
                "Inactive crew members cannot be assigned: "
                + ", ".join(inactive_names)
            )

        return self


def display_mission(mission: SpaceMission) -> None:
    """Print the mission details and its crew roster."""
    print(f"Mission: {mission.mission_name}")
    print(f"ID: {mission.mission_id}")
    print(f"Destination: {mission.destination}")
    print(f"Duration: {mission.duration_days} days")
    print(f"Budget: ${mission.budget_millions}M")

            f"  - {member.name} ({member.rank.value})"

        )

Fixing long lines the flake8 way

if self.contact_type == ContactType.TELEPATHIC and self.witness_count < 3:

    and self.witness_count < 3
):
    raise ValueError("...")

The parentheses let Python continue the expression across lines. Never "fix" it by splitting the logic into a separate variable unless you are sure the logic is still identical (see section 9 for what goes wrong).

7. The provided tools: data_generator.py and data_exporter.py

These two files are helpers to produce test data. You do not submit them, but they use more standard-library concepts worth understanding. They also show you what "realistic" data looks like for your models.

data_generator.py

  • @dataclass (DataConfig): a decorator that auto-writes __init__ and friends from annotated attributes. It is Python's built-in, validation-free cousin of BaseModel. Comparing the two is a good research topic.
  • random.seed(n): makes "random" numbers repeatable. Same seed gives the same data every run, which is essential for reproducible tests. Each generator uses seed, seed + 1, seed + 2 so they do not mirror each other.
  • random.choice, randint, uniform: pick from a list, an integer in a range, a float in a range.
  • datetime and timedelta: date arithmetic. base_date - timedelta(days=30) is "30 days earlier". .isoformat() converts to the ISO string that Pydantic can parse back.
  • Three generator classes (SpaceStationGenerator, AlienContactGenerator, CrewMissionGenerator): each builds plain dictionaries modelled on your exercises. For example, physical contacts are generated as verified and telepathic contacts get at least 3 witnesses.
  • The generator is not perfectly aligned with your rules. It adds a message to signals above 6.0 only 70% of the time, so a signal above 7.0 can come out with no message, which your Exercise 1 validator rejects. Real data often breaks strict rules, which is exactly why validation exists.

data_exporter.py

  • pathlib.Path: object-oriented file paths. Path("a") / "b.json" joins path parts; mkdir(exist_ok=True) creates a folder safely.
  • json.dump(data, f, indent=2, ensure_ascii=False): write Python data as JSON. indent pretty-prints; ensure_ascii=False keeps non-ASCII characters readable.
  • csv.DictWriter: writes a list of dictionaries to CSV, using dictionary keys as the header row.
  • Recursive flattening (_flatten_dict): CSV is flat, but a mission contains a nested crew list. The function walks the structure and builds keys like crew_0_name. A function calling itself to handle nested structure is called recursion.
  • Python-literal export (_format_python_data): JSON writes true/false/null, but Python needs True/False/None, so it writes valid Python source by hand.
  • create_test_scenarios(): deliberately builds invalid data (station ID too long, negative power, "WRONG_FORMAT" contact ID, telepathic with 1 witness). These are perfect inputs to try against your models.
Use them for self-testing

Load generated_data/invalid_stations.json and invalid_contacts.json, feed each dictionary to your model with Model(**item) (the ** unpacks a dict into keyword arguments), and confirm each one raises a ValidationError.

import json
from pydantic import ValidationError

with open("generated_data/invalid_contacts.json") as f:
    items = json.load(f)

for item in items:
    try:
        AlienContact(**item)
        print("UNEXPECTEDLY VALID:", item["contact_id"])
    except ValidationError as error:
        print("rejected:", error.errors()[0]["msg"])

9. Bugs we actually hit (and why)

Bug 1: the empty error message

The first version of the Exercise 1 demo printed nothing after Expected validation error:. The telepathic rule was not firing, so no ValidationError was raised and the except block never ran. See Bug 2 for why.

Bug 2: the "shortened" condition that was never true

broken

condition = ContactType.TELEPATHIC and self.witness_count < 3
if self.contact_type == condition:
    raise ValueError("...")

correct

if (
    self.contact_type == ContactType.TELEPATHIC
    and self.witness_count < 3
):
    raise ValueError("...")

Why the broken one fails

The and operator in Python does not return True/False. It returns one of its operands:

  • A and B returns A if A is falsy, otherwise B.
  • ContactType.TELEPATHIC is truthy (an Enum member is truthy by default), so ContactType.TELEPATHIC and (witness_count < 3) evaluates to just (witness_count < 3), a plain True or False.
  • Then self.contact_type == condition compares an Enum member to a bool, which is never equal.

The rule silently did nothing, and the sneaky part is that the code ran without any error. The fix is to compare contact_type against the Enum member inside the and, as two separate comparisons.

Lesson

Silent logic bugs are worse than crashes. When a validator "seems to work" on valid data, always test it against data that should fail. This is exactly what the correction sheet asks you to do live.

Bug 3: flake8 E501 (line too long)

The single-line condition was over 79 characters. The cause of Bug 2 was a rushed attempt to shorten it. The correct fix is wrapping in parentheses.

Bug 4: fragile prefix removal

Pydantic adds Value error, to messages raised from validators. Using .replace("Value error, ", "") removes the text anywhere it appears; checking startswith and slicing only removes it at the start, which is more precise.

Bug 5: GitHub access limitation

Not a code bug, but worth noting: running the three scripts locally and comparing the output to the subject's expected output is the reliable self-check. Add flake8 and mypy to that routine.
