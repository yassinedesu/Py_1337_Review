✗ Needs Correction What Was Incorrect
✗ "raise stops the program"

This was the most critical misconception. raise does NOT stop the program — it only signals that something went wrong. What happens next depends entirely on whether a try/except catches it.

raise ValueError("bad input")
# ↑ does NOT stop the program
# it just throws the exception upward
# except is what decides what happens next

Think of it: raise = throw the ball. except = catch it. If no one catches it, it hits the floor (crash).

✗ "We should always handle every exception"

Catching every exception with a broad except Exception can be worse than crashing. If a NameError or IndexError from a bug in your logic gets swallowed, your program keeps running with incorrect data — silently corrupting results. Sometimes a crash is the honest, correct behavior.

# DANGEROUS — hides real bugs
try:
    result = complex_sensor_calculation()
except Exception:
    print("something went wrong")
    # program continues with wrong/missing data ← worse than crash

✗ except GardenError catches only GardenError itself

You said it would only catch GardenError, not its subclasses. In Python, exception catching respects inheritance — catching a parent catches all its children too. PlantError and WaterError ARE GardenErrors.

class PlantError(GardenError): pass

try:
    raise PlantError("wilting!")
except GardenError as e:
    print(e)  # ← this DOES catch it
✗ Polymorphism confused with inheritance

You initially described polymorphism as "subclass inherits from parent" — that's inheritance. Polymorphism is specifically when different subclasses are treated as their parent type but respond differently. Inheritance is the mechanism; polymorphism is the behavior that results.

# Inheritance: Dog gets everything from Animal
# Polymorphism: Dog and Cat are both treated as Animal,
#               but speak() behaves differently for each

animals: list[Animal] = [Dog(), Cat()]
for a in animals:
    a.speak()  # same call, different result — that's polymorphism
⚠ Be Aware Things to Review & Watch Out For
⚠ An exception is an object, not just a condition

In Python, exceptions are instances of classes. When you write raise ValueError("bad input"), you're creating an object of type ValueError with a message attribute. This is why you can access str(e), why you can subclass them, and why except ValueError as e binds that object to e.

⚠ try/except vs if/else — not just about crashes

Your answer focused on "preventing crashes." But the deeper advantage is that try/except keeps your happy-path code clean and uncluttered. With if/else, you must check return values at every call site. With exceptions, errors announce themselves — they cannot be silently ignored.

⚠ finally runs even when exception is NOT caught

You understood finally runs on success and caught errors. Don't forget: if an exception propagates all the way up uncaught and the program is about to crash, finally still runs first. This guarantees cleanup even in worst-case scenarios.

⚠ mypy and type hints are required — don't skip them

The module requires type hints on all functions and mypy compliance. Pay special attention to return types when exceptions are possible — a function that raises should still declare its return type for the happy path. mypy will also flag intentional TypeError code (Exercise 2) — that's expected and acceptable.

The Exception Hierarchy in Python

All exceptions inherit from BaseException. Most you'll use inherit from Exception. KeyboardInterrupt and SystemExit inherit from BaseException directly — this is why bare except: is dangerous, it catches those too.

BaseException
├── KeyboardInterrupt  # Ctrl+C
├── SystemExit         # sys.exit()
└── Exception          # ← everything you'll normally use
    ├── ValueError
    ├── TypeError
    ├── FileNotFoundError
    └── GardenError    # your custom ones live here
        ├── PlantError
        └── WaterError
The Golden Rule of Exception Handling

Catch exceptions at the level where you can meaningfully respond to them. If you can't do anything useful with an exception where it's raised — let it propagate. Don't catch what you can't handle.
