Concept 1

Abstract classes (ABC)

An abstract class defines a contract: a list of methods every subclass must provide. You can't create an instance of it directly, and you can't create an instance of a subclass that skipped any of the required methods.

from abc import ABC, abstractmethod

class DataProcessor(ABC):
    @abstractmethod
    def validate(self, data: Any) -> bool: ...

    @abstractmethod
    def ingest(self, data: Any) -> None: ...

    def output(self) -> tuple[int, str]:   # concrete: shared, not overridden
        return self._storage.pop(0)

What exactly is enforced?

  • The subclass must define every abstract method with a real body. Having the right name isn't enough if it is still the abstract one.
  • The error is a TypeError, raised at instantiation (NumericProcessor()), not when the class is defined. You can define an incomplete subclass; you just can't build an object from it.
  • Abstract classes can also contain concrete methods (like output, remaining, total_processed). That is how inheritance gives you code reuse while subclasses specialise the rest.
class Broken(DataProcessor):
    def validate(self, data: Any) -> bool: return True
    # forgot ingest()

Broken()   # TypeError: Can't instantiate abstract class Broken ... abstract method 'ingest'
Concept 2

Metaclasses: how ABC actually works

In Python, classes are objects too. A metaclass is the class of a class: it decides how a class gets built.

type(42)       # <class 'int'>   → 42 is an instance of int
type(int)      # <class 'type'>  → int is an instance of type (its metaclass)
type(DataProcessor)   # <class 'abc.ABCMeta'>

Default metaclass is type. ABC simply sets metaclass=ABCMeta, so every class inheriting from it is built by ABCMeta.

Precise mechanism
  1. When a class is created, ABCMeta scans it for methods marked @abstractmethod and stores the still-unimplemented names in __abstractmethods__.
  2. When you call MyClass(), object creation (object.__new__) checks that set. If it is non-empty → TypeError.

Short version for your defense: metaclass = class factory; ABCMeta tracks abstract methods; instantiation fails while any remain.

Concept 3

Method overriding (and what it is not)

Definition

Overriding = a subclass redefines a method it inherited from its parent, replacing the parent's behaviour for its own instances.

The word inherited is the key. Two unrelated classes that happen to share a method name is not overriding.

# parent
def processor_name(self) -> str:
    return self.__class__.__name__

# NumericProcessor overrides it
def processor_name(self) -> str:
    return "Numeric Processor"
TermMeaningIn Python
OverridingSubclass replaces an inherited methodFully supported (used all over this project)
OverloadingSame name, different signatures, chosen by argumentsNot natively supported (last definition wins)

Implementing abstract methods is also overriding: the subclass provides the body for a method the parent only declared.

Concept 4

Polymorphism

Polymorphism (subtype polymorphism): code written against a base type works with any subclass, and each subclass reacts in its own way to the same call.

for proc in self._processors:      # each is "a DataProcessor"
    if proc.validate(item):         # Numeric? Text? Log? DataStream doesn't care
        proc.ingest(item)

DataStream never writes if isinstance(x, NumericProcessor). It calls validate and ingest and each class does its own thing.

Why it's useful (the question the subject asks)

  • Extensibility: add a new processor type, register it, and DataStream is untouched.
  • Decoupling: the stream depends on the interface, not on concrete classes.
  • No type-checking chains: no growing if/elif on types.
Concept 5

LSP, Any, and the intentional mypy warning

What is mypy?

mypy is a static type checker. It reads your annotations and reports inconsistent types without running the code. It never changes runtime behaviour; annotations are just hints Python itself ignores.

Liskov Substitution Principle (LSP)

Anywhere a base type is expected, any subclass should be usable without surprises. The base class promises ingest(data: Any), so in theory every subclass should accept anything. But NumericProcessor.ingest narrows to numbers only: that is the tension.

# base
def ingest(self, data: Any) -> None

# NumericProcessor narrows it
def ingest(self, data: Union[int, float, list[Union[int, float]]]) -> None

Why the warning appears in the test

num_proc = NumericProcessor()
num_proc.ingest("foo")   # mypy: Argument 1 has incompatible type "str"

num_proc is declared as a NumericProcessor, so mypy checks the narrow signature and sees a str being passed. That is the deliberate "bad call" the subject asks for, which is why you silence it with # type: ignore[arg-type].

Why a runtime guard is still needed

Because the contract is loose (Any in the base), the type checker can't protect every path. If someone holds a variable typed as DataProcessor, mypy will accept .ingest("foo"), and only your runtime check stops it:

if not self.validate(data):
    raise TypeError("Improper numeric data")

Hence the pattern: validate first, then ingest, with ingest raising if you skip validation.

Exercise 0

Design decisions in your processors

Storage and rank

self._storage: list[tuple[int, str]] = []   # FIFO queue of (rank, text)
self._counter: int = 0                       # total ever ingested
  • output() pops index 0 → oldest first (FIFO) and removes it.
  • rank comes from _counter, which only goes up.
Why _counter, not len(self._storage)?
ingest a,b,c   → [(0,a),(1,b),(2,c)]
output()       → [(1,b),(2,c)]
ingest d       → len = 2 → rank 2   ← collides with c!
              → [(1,b),(2,c),(2,d)]

A growing counter keeps ranks unique and stable even after items are removed. It also doubles as "total items processed" for the stats.

Validation details worth knowing

  • bool is a subclass of int in Python, so isinstance(True, int) is True. Your code excludes it explicitly with not isinstance(data, bool).
  • Lists must be non-empty and every element must match; a mixed list like ['Hi', 5] is rejected by every processor.
  • Numeric items are converted with str(item); logs are formatted as "LEVEL: message".

Unpacking list vs single value

items = data if isinstance(data, list) else [data]
for item in items: ...

Normalises "one thing or many things" so one loop handles both.

Concept 6

Composition vs inheritance

Inheritance = "is a"

NumericProcessor is a DataProcessor.

Composition = "has a"

DataStream has a list of DataProcessors.

class DataStream:
    def __init__(self) -> None:
        self._processors: list[DataProcessor] = []

If DataStream inherited from DataProcessor:

  • It would be forced to implement validate and ingest, which make no sense for a router.
  • The relationship would be wrong semantically: a stream is not a processor.
  • It would carry a single _storage instead of managing several processors.

Rule of thumb: inherit when it is-a, compose when it has-a.

Exercise 1

DataStream routing

def process_stream(self, stream: list[Any]) -> None:
    for item in stream:
        routed = False
        for proc in self._processors:
            if proc.validate(item):
                proc.ingest(item)
                routed = True
                break                 # first match wins
        if not routed:
            print("DataStream error - ", end="")
            print(f"Can't process element in stream: {item}")

Key behaviours

  • First match wins: after break, later processors never see that item.
  • Registration order = priority. A hypothetical GenericProcessor whose validate accepts anything would steal every item if registered first, and the specialised processors would get nothing.
  • The error is printed only when no processor accepts the item (routed stays False). Two processors both accepting an item does not cause an error; it just goes to the first.
  • In the subject's example the first batch has only a NumericProcessor registered, so text and logs produce error lines; the second pass with all three registered handles them.

A more robust design could detect overlapping validators or add an explicit priority, but the subject keeps it simple.

Exercise 2

Duck typing and Protocol

Duck typing (the idea)

"If it has the method, just call it." Python doesn't check the declared type of an object, only that the attribute exists when you use it. No import needed, and it long predates type hints.

Protocol (the tool)

A way to describe that expected shape to mypy, so the type checker can verify duck-typed code statically.

class ExportPlugin(Protocol):
    def process_output(self, data: list[tuple[int, str]]) -> None:
        ...

class CSVExportPlugin:          # no parent class mentioned at all
    def process_output(self, data: list[tuple[int, str]]) -> None:
        print("CSV Output:")
        print(",".join(v for _, v in data))

ABC vs Protocol

ABC (nominal)Protocol (structural)
RelationshipMust explicitly inherit: class X(Base)None needed; matching method shape is enough
EnforcementAt runtime (TypeError on instantiation)Only by mypy; nothing at runtime
Shared codeYes, concrete methods in the baseNo, it only describes an interface
Best forFamilies of classes you control that share logicPlugins, third-party or unrelated classes
Uses overriding?YesNo: there's no parent to override, each class independently implements the method
Common mix-ups to avoid
  • Protocol is not overriding and not overloading.
  • Duck typing is the general concept; Protocol is how mypy formalises it.
  • Protocol checks are static. At runtime, Python just calls plugin.process_output(...) on whatever object it receives (the @runtime_checkable decorator exists but isn't used here).

What do the three dots ... mean?

It's the Ellipsis literal, used here as a placeholder body meaning "no implementation, just the signature". It plays the same role as pass. The body of a Protocol method is never executed by your plugins.

Exercise 2

output_pipeline

def output_pipeline(self, nb: int, plugin: ExportPlugin) -> None:
    for proc in self._processors:
        collected: list[tuple[int, str]] = []
        for _ in range(nb):
            try:
                collected.append(proc.output())
            except IndexError:     # processor ran out of items
                break
        if collected:
            plugin.process_output(collected)
  • Once per processor: matches the subject's example (separate CSV/JSON blocks for numeric, text, and logs). Merging everything into one call would mix unrelated data types in a single row and lose which processor produced what.
  • try/except IndexError: output() raises when empty, so asking for 5 items from a processor holding 3 simply stops at 3. This is the "exception handling protects the stream" requirement.
  • if collected: skips the plugin call entirely if a processor had nothing, avoiding an empty "CSV Output:" header.
  • The same plugin object works with any processor's data because it only needs process_output.
Housekeeping

flake8, imports, and the small bugs

Imports

Only abc and typing are allowed. Both styles are valid and identical at runtime; the real rule is be consistent:

# Option A (clean): names imported directly
from typing import Any, Union, Protocol
# ... then use Any / Protocol everywhere, no "typing." prefix

# Option B: module import
import typing
# ... then use typing.Any / typing.Protocol everywhere
What went wrong for you

You removed import typing while the code still contained typing.Protocol and list[typing.Any], hence NameError: name 'typing' is not defined. If you switch to Option A, replace every typing.X usage too. Fixing only one spot just moves the error to the next one.

The end=None bug

print("DataStream error - ", end=None)   # None → falls back to "\n" (default)
print("DataStream error - ", end="")     # stays on the same line ✔

The subject's expected output shows the error on a single line, so use end="".

Things worth re-checking

  • Run flake8 and mypy on each file. The only mypy complaint you should deliberately keep is the invalid ingest("foo") test in ex0.
  • In process_stream, proc is typed DataProcessor and item is Any, so mypy may report a "unused type: ignore" if configured strictly. If so, remove that comment.
  • Docstrings: a class with two consecutive string literals only treats the first as the docstring. Put the whole description in one docstring.
  • Compare your output text character by character with the subject's examples (spacing, capitalisation, wording).
Prepare

Defense Q&A: click to reveal

What happens if I instantiate a subclass that doesn't implement an abstract method?
TypeError at instantiation. ABCMeta records unimplemented abstract names in __abstractmethods__, and object creation refuses while that set isn't empty.
Define method overriding in one sentence.
A subclass redefines a method inherited from its parent, replacing the parent's behaviour for its own instances.
Define polymorphism in one sentence.
One interface, many behaviours: code written against a base type calls the same method on different subclasses and each responds in its own way.
Why does ingest have a narrower signature than the base?
Each processor accepts specific types, so the signature documents that. It stretches LSP since the base says Any, which is why a runtime validate guard plus TypeError is needed and why the deliberate bad call triggers a mypy warning.
Why is output not abstract?
Its behaviour is identical for every processor (pop the oldest item). Putting it in the base class gives code reuse; only what varies (validate, ingest) is abstract.
Composition or inheritance for DataStream, and why?
Composition. A stream isn't a processor; it holds and coordinates several. Inheriting would force meaningless abstract methods and a wrong "is-a".
What if two processors accept the same data?
The first registered one gets it, because of the break. Registration order is effectively priority.
Difference between duck typing and Protocol? Between ABC and Protocol?
Duck typing is the runtime idea; Protocol lets mypy check it statically. ABC needs explicit inheritance and is enforced at runtime; Protocol only needs a matching method shape and is checked by mypy only.
How would you add a new processor type live (e.g., BooleanProcessor)?
Subclass DataProcessor, implement validate and ingest (store as (counter, str), raise TypeError on bad input), override processor_name, then register_processor. Nothing in DataStream changes.
How would you add a new export format (e.g., XML)?
Write a class with process_output(self, data: list[tuple[int, str]]) -> None. No inheritance needed; pass it to output_pipeline.
Why exception handling in output_pipeline?
Asking for more items than a processor holds would raise IndexError and could abort the whole pipeline; catching it lets each processor export what it has.
