The big picture

This module is about design patterns: reusable ways of structuring classes so that code stays flexible when requirements change. You are not learning new syntax; you are learning how to arrange classes you already know how to write.

ex0Abstract Factory
A class whose only job is to create objects. The caller asks the factory for “a base creature” and never names the concrete class.
ex1Capabilities
Optional behaviours (heal, transform) defined as separate abstract classes and mixed into creatures with multiple inheritance.
ex2Strategy
A battle “script” wrapped in its own class. The tournament calls strategy.act(creature) without knowing what the script does.

All three rest on one foundation: abstract classes (a contract that says “whoever inherits from me must implement these methods”) and polymorphism (calling the same method on different objects and getting different behaviour).

Concepts, one by one

ex0Abstract classes: ABC and abstractmethod

What it is

An abstract class is a class you are not allowed to instantiate. It exists to define a contract: a list of methods every subclass must provide. You make one by inheriting from ABC (from the abc module) and marking required methods with @abstractmethod.

AnalogyA job description for “Chef”. You can’t hire a job description; you hire a pastry chef or a grill chef. The description guarantees whoever you hire can cook().

The problem it solves

Without it, nothing stops someone from creating a half-finished Creature and calling attack() on something that has no attack. With it, Python refuses early, at creation time, instead of failing mysteriously later.

How it works inside

ABC uses a metaclass called ABCMeta. When a class is defined, it collects every method marked abstract into a set called __abstractmethods__. A subclass that overrides a method removes it from that set. When you call SomeClass(), Python checks: is the set empty? If not, it raises TypeError: Can't instantiate abstract class ... with abstract method ....

from abc import ABC, abstractmethod

class Creature(ABC):
    @abstractmethod
    def attack(self) -> str:       # required: every subclass MUST define this
        pass

    def describe(self) -> str:     # concrete: shared by all subclasses for free
        return "I am a creature"

Creature()          # TypeError: Can't instantiate abstract class Creature
class Dud(Creature): pass
Dud()               # TypeError too: attack() was not implemented
class Fire(Creature):
    def attack(self) -> str:
        return "Ember!"
Fire()              # works

Abstract vs concrete methods

  • Abstract method: declared, not implemented. Every subclass must supply it. Your Creature.attack is abstract because each creature attacks differently.
  • Concrete method: fully implemented, inherited as-is. Your Creature.describe is concrete because every creature is described the same way (“X is a Y type Creature”).
  • An abstract class can have an __init__ and attributes. Yours stores name and creature_type.
Say it out loud — “Why are abstract classes useful?” They define a contract that all subclasses must follow, so code that uses a Creature can rely on attack() existing without knowing which concrete creature it has. They also prevent creating incomplete objects: Python raises TypeError if you try to instantiate the abstract class or a subclass that forgot to implement an abstract method.
Common mistakes Forgetting to inherit from ABC (then @abstractmethod is silently ignored and the class can be instantiated). Forgetting to implement one abstract method in a subclass. Believing an abstract class must have only abstract methods (it doesn’t; mixing is normal).
About “decorators” in the correction sheet The sheet asks whether “decorators are avoided”, but @abstractmethod is a decorator, and it is the standard way to use the abc module that the subject explicitly authorizes (import abc). The sheet’s intent is: don’t use other decorators (@property, @staticmethod, @classmethod, @dataclass, custom ones). Your code uses only @abstractmethod. If asked, say exactly that.

ex0Inheritance, super() and polymorphism

What it is

Inheritance: Flameling(Creature) receives everything Creature has. Polymorphism: the same call, creature.attack(), runs different code depending on the real class of the object.

class Flameling(Creature):
    def __init__(self) -> None:
        super().__init__("Flameling", "Fire")   # run Creature's __init__ to set name and type
    def attack(self) -> str:
        return "Flameling uses Ember!"

Why polymorphism matters here: battle.py has a function test_factory(factory) that works with any factory and calls describe() and attack() on whatever comes out. That function is never edited when you add a new creature family.

Say it out loudPolymorphism means one interface, many behaviours. My test function takes a Creature and calls attack(); what runs depends on whether it is a Flameling or an Aquabub, but the calling code doesn’t change.

ex0Abstract Factory pattern

What it is

An abstract factory is an abstract class whose methods create objects. Concrete factories override those methods, and each one produces a different family of related objects. Here, a family = (base creature, evolved creature).

AnalogyA car blueprint with two slots: “economy car” and “luxury car”. Ford and Toyota both follow it. You tell the dealership “give me the economy car” and it hands you a Fiesta or a Yaris depending on which manufacturer you chose. You never say the model name.

The problem it solves

If client code writes Flameling() directly, it is glued to that class: to use another family you must edit the client. With a factory, the client writes factory.create_base() and works with any family. It also guarantees the base and evolved creatures you get belong together (Flameling and Pyrodon never mix with Torragon).

How it works

class CreatureFactory(ABC):               # the abstract factory: the contract
    @abstractmethod
    def create_base(self) -> Creature: ...
    @abstractmethod
    def create_evolved(self) -> Creature: ...

class FlameFactory(CreatureFactory):      # a concrete factory: one family
    def create_base(self) -> Creature:
        return Flameling()
    def create_evolved(self) -> Creature:
        return Pyrodon()

Notice the return type is Creature, not Flameling. That is deliberate: callers only see the abstract type.

Say it out loud — “Explain the Abstract Factory”It’s a factory interface that creates families of related objects. CreatureFactory declares create_base and create_evolved. FlameFactory and AquaFactory implement them for their families. The client function receives a factory and never mentions a concrete creature, so I can add a new family by adding a new factory, without touching the client code.
Don’t confuse withA plain “factory function” that creates one kind of object. The abstract factory pattern is specifically about an abstract creator interface with interchangeable concrete creators that produce families.

ex0Packages, __init__.py, encapsulation, absolute imports

What it is

A package is a folder Python treats as importable. __init__.py marks it and decides what the package exposes when someone writes from ex0 import ....

Why your __init__.py files look the way they do

# ex0/__init__.py
from ex0.CreatureFactory import CreatureFactory
from ex0.FlameFactory import FlameFactory
from ex0.AquaFactory import AquaFactory
__all__ = ["CreatureFactory", "FlameFactory", "AquaFactory"]

The subject says: “Your ex0 package cannot expose concrete Creature directly, it must only expose factories.” So __init__.py imports only factories. A user of the package gets FlameFactory and nothing named Flameling in the package’s public namespace. This is encapsulation: the concrete classes are implementation details.

__all__ lists the public names (it controls from ex0 import * and documents intent).

Honest caveatThe concrete modules (ex0/Flameling.py) still exist and could be imported by path. “Not exposed” means the package’s public interface doesn’t offer them; it is a design convention, not a security wall. That is fine and normal in Python.

Absolute imports

You write from ex0.Creature import Creature (full path from the repository root) rather than from .Creature import Creature (relative). The correction sheet explicitly asks for absolute imports between exercises, e.g. ex1 importing from ex0.

Running with module syntax

The sheet mentions python3 -m ex0.main. In your subject the scripts sit at the repository root and are run as python3 battle.py, python3 capacitor.py, python3 tournament.py, which matches the subject examples. Both work because Python adds the script’s folder (the repo root) to the import path, so import ex0 resolves.

Say it out loud__init__.py turns a folder into a package and controls its public API. I only export the factories so users can’t depend on the concrete creature classes. I use absolute imports so each file states exactly where its dependencies live.

ex1Multiple inheritance and the MRO

What it is

A class may have more than one parent: class Sproutling(Creature, HealCapability). It receives the methods of both.

AnalogyA Swiss Army knife: it is a knife and a screwdriver. The two tool designs were made independently; the knife body just carries both.

The problem it solves

Suppose healing lived inside Creature. Then every creature, even a Flameling, would have heal(). If you instead made HealingCreature and TransformingCreature subclasses, you could never express “a creature that does both” without a third class, then a fourth… Multiple inheritance lets you compose abilities.

The MRO (Method Resolution Order)

When you call a method, Python searches classes in a fixed order. For your classes:

Sproutling.__mro__
# (Sproutling, Creature, HealCapability, ABC, object)

Rule of thumb: the class itself first, then parents left to right, with shared ancestors (ABC, object) last. In your code there is no conflict because the parents own different method names: Creature owns attack/describe, HealCapability owns heal.

Why you call both __init__ methods explicitly

class Shiftling(Creature, TransformCapability):
    def __init__(self) -> None:
        Creature.__init__(self, "Shiftling", "Normal")   # sets name, creature_type
        TransformCapability.__init__(self)               # sets is_transformed = False

Creature.__init__ doesn’t call super().__init__(), so a single super().__init__() in the child would only reach Creature and the capability’s state would never be initialised. Calling each parent’s __init__ by name guarantees both run. (For Sproutling, HealCapability has no __init__ of its own, so that call just reaches object.__init__ and does nothing; harmless.)

Say it out loud — “Benefits of multiple inheritance / interfaces?”It lets me combine independent abilities in one class without building a huge hierarchy. A creature is a Creature and also has the heal capability. Each piece is defined once and reused. The danger is ambiguity when parents share method names, which Python resolves with the MRO; I avoid it by giving each interface its own distinct methods.

ex1Capability (interface) classes

What it is

A capability is an abstract class describing one ability, such as “can heal”. Python has no interface keyword, so an abstract class whose methods are all abstract plays that role.

class HealCapability(ABC):
    @abstractmethod
    def heal(self) -> str: ...

Key rule from the subject

“Capability abstract classes will not inherit from the Creature base class.” They must stay independent so that one day a Building or a Player could also be healable. If HealCapability inherited from Creature, every healable thing would have to be a Creature.

Say it out loud — “Capability vs base class?”A base class says what something is (a Creature). A capability says what it can do (heal, transform). Capabilities are separate so they can be attached to any class and don’t force a hierarchy.

ex1Persistent state

The subject says: “An attribute is used to make the state persistent and it impacts the attack implementation.” That attribute is is_transformed.

# state starts False
creature.attack()      # "Shiftling attacks normally."
creature.transform()   # sets is_transformed = True
creature.attack()      # "Shiftling performs a boosted strike!"   ← same method, new result
creature.revert()      # sets is_transformed = False
creature.attack()      # "Shiftling attacks normally."

The object remembers what happened to it. transform() writes the flag; attack() reads it. The flag lives on the instance (self.is_transformed), so each creature has its own.

Common mistakesForgetting to initialise is_transformed = False (you’d get AttributeError on first attack()). Making it a class-level variable so all creatures share one flag. Not resetting it in revert().

ex2Strategy pattern

What it is

You put each algorithm (here: each battle routine) in its own class behind a common interface, then pass the chosen one around. The user of the strategy just calls act().

AnalogyA GPS offering “fastest”, “shortest”, “avoid highways”. All answer “how do I get there?”, each in its own way, and you can swap them without rebuilding the app.

The problem it solves

Without it, the tournament loop would contain:

if isinstance(creature, TransformCapability):
    creature.transform(); creature.attack(); creature.revert()
elif isinstance(creature, HealCapability):
    creature.attack(); creature.heal()
else:
    creature.attack()

Every new capability means editing this loop. With strategies, the loop is one line, strategy.act(creature), and a new behaviour is a new class. This follows the Open/Closed principle: open for extension, closed for modification.

The two methods

  • is_valid(creature) -> bool: a question (“can this creature use me?”). Never raises.
  • act(creature) -> None: the action. Raises InvalidStrategyError if called with an incompatible creature.
Say it out loud — “Strategy vs Factory?”The factory is about creating objects; the strategy is about behaviour, swapping how something acts. In my tournament, a tuple (factory, strategy) says “create this creature, then make it fight like this”.

ex2Custom exceptions and graceful handling

class InvalidStrategyError(Exception):
    pass

A dedicated exception tells readers exactly what went wrong and lets you catch only that error. except InvalidStrategyError won’t accidentally swallow an unrelated bug such as a KeyError, which a bare except Exception would.

The subject requires: “If the act method is called with an invalid combination, a dedicated exception is raised with a clear message.” and “Your functions should handle exceptions gracefully to avoid crashes.” Your battle() catches the error and prints Battle error, aborting tournament: ... instead of crashing. This matters because the sheet says an uncontrolled termination in defence means a final grade of 0.

Say it out loudI raise InvalidStrategyError in act() when the creature lacks the needed capability. The tournament function catches it, prints a clear message and stops, so the program never crashes. is_valid exists so callers can check first without using exceptions.

allType hints, mypy, flake8, isinstance

  • Type hints: def attack(self) -> str. Required on every function (parameters and return). mypy checks them. Yours: Success: no issues found in 27 source files.
  • flake8: style checker. Yours reports zero errors. The usual enemy is line length (79 characters max).
  • isinstance(creature, HealCapability): asks “does this object inherit from that class?” It works with capabilities because the creature really inherits from them. This is how is_valid decides.
  • Tuple[CreatureFactory, BattleStrategy]: a fixed pair; Opponent is a type alias so signatures stay readable.
  • Round-robin loop: for i ... for j in range(i + 1, n) visits every unordered pair exactly once. With 3 opponents you get 3 fights (matches the subject example).
About # type: ignore in your strategies Your act() methods write transform_creature: TransformCapability = creature # type: ignore. It works, but an evaluator may ask why. Answer: is_valid already proved the type, but mypy can’t see that through a method call, so the comment silences it. A cleaner alternative (optional) is to test with isinstance directly inside act() and raise; mypy then narrows the type automatically with no ignore needed.
def act(self, creature: Creature) -> None:
    if not isinstance(creature, TransformCapability):
        raise InvalidStrategyError(
            f"Invalid Creature '{creature.name}' for this aggressive strategy"
        )                                   # (split over two lines to stay under 79 chars)
    print(creature.transform())             # mypy now knows creature has transform()
    print(creature.attack())
    print(creature.revert())

ex2/DefensiveStrategy.py
class DefensiveStrategy(BattleStrategy):
    def is_valid(self, creature: Creature) -> bool:
        return isinstance(creature, HealCapability)

    def act(self, creature: Creature) -> None:
        if not self.is_valid(creature):
            msg = (
                f"Invalid Creature '{creature.name}'"
                " for this defensive strategy"
            )
            raise InvalidStrategyError(msg)
        heal_creature: HealCapability = creature  # type: ignore
        print(creature.attack())
        print(heal_creature.heal())
tournament.py — the single battle function
Opponent = Tuple[CreatureFactory, BattleStrategy]

def battle(opponents: List[Opponent]) -> None:
    print("*** Tournament ***")
    print(f"{len(opponents)} opponents involved")
    for i in range(len(opponents)):
        for j in range(i + 1, len(opponents)):          # each pair exactly once
            factory_a, strategy_a = opponents[i]
            factory_b, strategy_b = opponents[j]
            creature_a = factory_a.create_base()
            creature_b = factory_b.create_base()
            print("\n* Battle *")
            print(creature_a.describe()); print(" vs."); print(creature_b.describe())
            print(" now fight!")
            try:
                strategy_a.act(creature_a)              # each uses ITS strategy
                strategy_b.act(creature_b)
            except InvalidStrategyError as error:
                print(f"Battle error, aborting tournament: {error}")
                return                                  # abort the tournament

Concepts that appear only in the sheet

Polymorphic container (Deck)

A Deck holds a list[Card]. Because every item is a Card, add_card, remove_card, shuffle, draw_card work identically for spells, artifacts and creatures. get_deck_stats() returns summary info (e.g. total cards, count per type, average cost). Polymorphism lets the deck call card.get_card_info() without knowing the card’s type.

class Deck:
    def __init__(self) -> None:
        self.cards: list[Card] = []
    def add_card(self, card: Card) -> None:
        self.cards.append(card)
    def draw_card(self) -> Card:
        return self.cards.pop(0)        # no decorators, no external libs

Interfaces with all abstract methods

The sheet insists Combatable and Magical contain only abstract methods. That is what makes them pure interfaces rather than partial base classes. Example: Combatable declares attack() and defend(); Magical declares cast_spell().

EliteCard: inheriting three contracts

class EliteCard(Card, Combatable, Magical):
    # must implement: play() from Card, attack()/defend() from Combatable,
    # cast_spell() from Magical. Miss ONE and Python refuses to create it.

Python checks the union of every abstract method of every parent. “Does the implementation make sense?” means the methods should actually reflect an elite card that fights and casts spells.

GameEngine: configured, not hard-wired (dependency injection)

The engine receives a factory and a strategy rather than creating them itself:

class GameEngine:
    def configure(self, factory: CardFactory, strategy: GameStrategy) -> None:
        self.factory = factory
        self.strategy = strategy

This is called dependency injection. The sheet’s “test pattern switching” means: run the engine with FantasyCardFactory then another factory, or AggressiveStrategy then another strategy, and show the engine code didn’t change.

Rankable, TournamentCard, TournamentPlatform

  • Rankable: another abstract interface (for example get_rank(), update_rank()). Reusable for any rankable thing.
  • TournamentCard(Card, Combatable, Rankable): interface composition; three contracts at once.
  • TournamentPlatform: the glue. register_card, create_match, get_leaderboard use all the previous pieces together (system-level integration).
The “don’t over-engineer” ruleThe sheet says “the focus is on patterns rather than complex game logic.” Simple strings and counters are fine. Evaluators want to see the structure, not a realistic game.

attack() is abstract. describe() and __init__ are concrete.
Explain the Abstract Factory pattern with your code.
CreatureFactory is the abstract factory with create_base() and create_evolved(). FlameFactory and AquaFactory are concrete factories, each producing one family. test_factory(factory) works with any of them and never names a concrete creature.
Why does your package only export factories?
Because the subject requires it, and because it’s encapsulation: callers depend on the factory interface, not on concrete creature classes, so I can change or add creatures without breaking users.
Why don’t HealCapability and TransformCapability inherit from Creature?
So they stay reusable. A capability describes an ability, not an entity. If it inherited from Creature, only creatures could ever heal or transform.
Why do you call Creature.__init__ and TransformCapability.__init__ separately?
Creature.__init__ doesn’t forward to super().__init__(), so a single super() call would never reach the capability. Calling each parent explicitly guarantees both name/type and is_transformed are initialised.
What is the MRO of Sproutling?
Sproutling → Creature → HealCapability → ABC → object. Python searches left to right. There’s no clash because the parents define different method names.
How does is_transformed change attack()?
transform() sets it to True; attack() checks it and returns the boosted message; revert() sets it back to False. It’s instance state, so each creature has its own.
What is the Strategy pattern and what does it replace?
It wraps each battle routine in its own class behind BattleStrategy. It replaces a chain of if isinstance(...) in the tournament loop. The loop just calls strategy.act(creature), and new behaviours are new classes.
What’s the difference between is_valid and act?
is_valid returns a bool (a safe check, never raises). act performs the sequence and raises InvalidStrategyError if the creature isn’t compatible.
Why a custom exception instead of Exception?
It names the exact failure and lets me catch only that case without hiding unrelated bugs. The tournament catches it and aborts cleanly instead of crashing.
How many fights happen with N opponents?
Every unordered pair once: N·(N−1)/2. With 3 opponents, 3 fights.
Why is @abstractmethod OK if “decorators are avoided”?
It’s the standard mechanism of the abc module, which the subject authorizes. No other decorators are used (no @property, @staticmethod, @dataclass…).
Why is there # type: ignore in your strategies?
After is_valid passes I know the creature has the capability, but mypy can’t infer that through a method call. A cleaner version uses isinstance directly in act(), which mypy narrows automatically.
How would you add a new creature family (e.g. Electric)?
Add two concrete creatures and an ElectricFactory(CreatureFactory), export the factory. No change to battle.py or tournament.py logic. That’s the point of the pattern.
How would you add a new strategy?
Create a new class inheriting BattleStrategy implementing is_valid and act. The tournament function stays untouched.
Why absolute imports?
The sheet asks for them. from ex0.Creature import Creature states the exact location from the repo root and works the same wherever the file is used.
